Week 1 measurement

Which number moved

Run on gpu1 against Qwen2.5 1.5B, 96 output tokens. Students produce this table themselves, then answer one question from it: do replicas help?

ConcurrencyTTFT p50TTFT p95ITL p50Throughput
119.5 ms19.5 ms13.2 ms74 tok/s
842.4 ms44.8 ms13.5 ms573 tok/s
3262.0 ms77.6 ms15.2 ms1,992 tok/s
64102.6 ms122.5 ms16.6 ms3,581 tok/s

64× the load bought 48× the throughput. TTFT rose 5.3×; ITL rose 1.25×. The time went into queueing, not decoding — so replicas help here and a bigger GPU does not. Answering that from the table, rather than from intuition, is the skill the whole course is built to produce.

Week 3 measurement

The knee is a config default

Sweep concurrency until throughput stops scaling. Students predict the limiting resource first; almost all of them say VRAM or GPU compute.

ConcurrencyTTFT p50TTFT p95ThroughputWaitingKV used
119.9 ms19.9 ms61 tok/s00.0%
64125.1 ms169.1 ms3,117 tok/s00.0%
128204.7 ms339.6 ms4,306 tok/s00.0%
256430.1 ms606.5 ms6,680 tok/s02.7%
384642.6 ms2,802 ms5,891 tok/s1283.6%

Throughput falls past the knee. Concurrency 256 → 384 buys 4.6× the tail latency to lose 12% of throughput. Under sustained load the engine pins at exactly 256 running with 144 queued — vLLM's default max_num_seqs — while the KV cache sits at 9.3% used. Over 90% of the memory budgeted in Week 2 is idle at saturation. The bottleneck is not the GPU, not the KV cache, but a config default nobody set.

Syllabus

Eight weeks, one stack

CUDA → vLLM → Kubernetes → NVIDIA GPU Operator/DCGM → Prometheus → KServe. One stack taught to depth beats ten frameworks taught to a demo.

Capstone

The output is evidence, not a chatbot

Students pick a real open problem in vLLM, llm-d, KServe or the GPU Operator. Even when the patch is not merged, a minimal reproducer and a defensible analysis are real engineering output — and they are exactly the signal AI-infrastructure interviews currently find missing.

Every capstone ships

  • A reproducible workload or failure
  • Measurements and a stated hypothesis
  • Root-cause analysis
  • A test, patch, controller or instrumentation change
  • A runbook
  • An upstream issue or pull request
  • A technical blog post

Viable subjects

  • Missing or misleading CUDA-graph metrics
  • GPU-memory attribution across sleep/wake
  • Warm-capacity semantics in an inference autoscaler
  • Per-request inference-time accuracy
  • GPU kernel and model-cache supply-chain integrity
  • Reproducing and detecting a distributed inference hang
